# 九寨沟景区智能服务 Agent —— 核心功能与代码逻辑详解

## 一、系统是什么

一句话：**这是一个针对「九寨沟风景名胜区」的 AI 智能客服 + 运营后台系统**。游客可以在网页上向它提问、获取路线推荐、提交反馈；管理员可以在后台审核反馈、查看运营数据、管理知识库。知识库内容来自公开可查证的九寨沟真实资料，来源与口径见根目录 `README_DATA.md`。

**技术栈全景：**
| 层级 | 技术 | 作用 |
|------|------|------|
| 前端 | Vue 3 + Vite | 游客界面 + 管理后台 |
| 后端 API | FastAPI（Python） | 提供所有 HTTP 接口 |
| 数据库 | PostgreSQL | 存景点、设施、文档、反馈等 |
| 缓存/队列 | Redis | 缓存检索结果 + 任务队列 |
| 向量检索 | pgvector 扩展 | 语义相似度搜索 |
| 后台任务 | arq + worker | 异步生成 embedding |
| AI 接入 | LLM API + Embedding API | 智能回答 + 向量化 |

## 三、核心流程逐一拆解

### 流程 0：启动时自动建表（可踩坑点）

`main.py` 的 `startup` 事件会在后端启动时自动执行：

```python
@app.on_event("startup")
def startup() -> None:
    if db_ready():           # 先探测数据库是否可达
        ensure_runtime_tables()   # 再自动建表
```

**`ensure_runtime_tables()`** 用 `CREATE TABLE IF NOT EXISTS` 一次性确保这些运行时表存在：
- `admin_users` 管理员账号
- `conversations` 会话
- `conversation_messages` 会话消息
- `agent_runs` Agent 运行审计
- `knowledge_versions` / `knowledge_reviews` 知识版本与审核
- `async_tasks` 异步任务（embedding）
- `system_settings` 系统设置

**启动时还顺带创建默认管理员账号**（密码用 bcrypt 哈希存储，绝不存明文）：
```python
hashed = bcrypt.hashpw(ADMIN_PASSWORD.encode(), bcrypt.gensalt()).decode()
conn.execute(text("INSERT INTO admin_users(email,password_hash) VALUES ..."))
```

> ⚠️ **新手注意**：这里用的是 `engine.connect()` + `text()` 原生 SQL，而不是 ORM 模型。这是合法的 SQLAlchemy 用法。

### 流程 1：游客提问 → 智能回答（核心中的核心）

入口是 `/api/v1/chat/stream`（SSE 流式）或 `/api/v1/chat/messages`（同步）。两者最终都调用同一个函数 `answer_sync()`：

```python
def answer_sync(request: ChatRequest) -> dict:
    started = time.perf_counter()
    cid = create_conversation(request.conversation_id)  # ① 建/复用会话
    intent = classify(request.message)                  # ② 判断意图
    ...
```

#### ① 意图识别 `classify()`

**这就是一个小型的"关键词路由 Agent"**，用简单的关键词匹配决定走哪条分支：

```python
def classify(message: str) -> str:
    if any(word in message for word in ("路线","怎么玩","老人","儿童","孩子","半天","一天")):
        return "recommendation"    # 要做路线推荐
    if any(word in message for word in ("反馈","投诉","建议","损坏")):
        return "feedback"          # 提交反馈
    if any(word in message for word in ("天气","客流","关闭","开放状态")):
        return "realtime"          # 实时信息
    return "qa"                    # 默认当作知识问答
```

> 这样设计的好处是**零成本**：不依赖大模型也能路由。缺点是不够智能，但作为第一版够用。

#### ② 知识检索 `retrieve()` —— 系统的"RAG 三层漏斗"

这是整个项目最精髓的部分，采用**三级检索策略**，从高级到兜底逐级降级。

**第 1 层：pgvector 向量检索（语义理解）**
```python
if vector:  # embedding 服务配置了才走这里
    rows = conn.execute(text("""
        SELECT ...
        FROM document_chunks c JOIN documents d ON (...)
        WHERE c.park_id=:park_id AND c.embedding IS NOT NULL
        ORDER BY c.embedding <=> CAST(:vector AS vector)  -- <=> 是余弦距离
        LIMIT :limit
    """), ...)
```
这里的 `< =>` 是 pgvector 的**余弦距离**运算符，数字越小越相似。它能把"下雨适合去哪"和知识库里"雨天建议去室内展厅"这样的语义匹配起来，不依赖字面相同。

**第 2 层：PostgreSQL 全文检索（FTS，关键词）**
```python
WHERE park_id=:park_id
  AND to_tsvector('simple', content) @@ plainto_tsquery('simple', :message)
```
用 PostgreSQL 自带的全文本搜索 `to_tsvector @@ to_tsquery` 做分词匹配。

**第 3 层：ILIKE 模糊匹配（兜底，中文安全）**
```python
WHERE park_id=:park_id AND (content ILIKE :q OR content ILIKE :q2)
```
因为 PostgreSQL 默认 FTS 对中文分词不好，所以最后用 `ILIKE`（不区分大小写的模糊查询）兜底，`q2` 用消息的第一个词再试一次。

**关键点还有缓存**：`retrieve` 开头 `cache_get(cache_key)`，结尾 `cache_set(...)`，相同问题 5 分钟内直接命中 Redis/内存缓存，不用重新检索。

#### ③ 生成回答 `generate_answer()`

```python
if LLM_MODE == "api" and LLM_BASE_URL and LLM_API_KEY:
    async with _llm_sem:      # 限制并发，防止打爆 API
        prompt = "你是九寨沟景区官方客服，只能依据给定资料回答。资料：..."
        response = await client.post(f"{LLM_BASE_URL}/chat/completions", ...)
        return response.json()["choices"][0]["message"]["content"]
```

**重要设计：LLM 可选**。没有配置 API Key 时（`LLM_MODE` 是 `fallback`），它会返回一个**纯规则式的答案**：

```python
if context:
    return "根据景区资料：\n" + 资料内容 + "\n以上信息来自当前景区知识库..."
return "暂未查询到足够信息，建议咨询游客服务中心。"
```

> 也就是说，**没有大模型也能演示整套系统**。这非常利于开发调试。

#### ④ 持久化与审计

`answer_sync` 的最后做两件事：
1. 把用户问题 + AI 回答（带引用）存入 `conversation_messages`
2. 调用 `save_run()` 把这次"Agent 运行动作"写入 `agent_runs`（记录意图、延迟、命中的文档、状态）

### 流程 2：流式回答（SSE 打字机效果）

`/api/v1/chat/stream` 返回 `StreamingResponse`，通过 SSE（Server-Sent Events）一段段推给前端：

```python
yield f"event: status\ndata: ...正在识别问题..."
yield f"event: status\ndata: ...正在检索景区知识..."
yield f"event: citations\ndata: ..."    # 引用来源
for token in result["message"].splitlines(True):
    yield f"event: token\ndata: ..."     # 逐行"打字"
yield f"event: result\ndata: ..."        # 完整结果
```

前端 `frontend/src/api.ts` 用 `fetch` 的 `ReadableStream` 读取，`streamChat(message, onEvent, ...)` 一句句按 `event:` 类型分发给组件更新界面。这就是你看到 AI **一个字一个字蹦出来**的效果。

### 流程 3：路线推荐 `build_recommendation()`

这是**纯规则算法**（没用 LLM），核心逻辑：

```python
# 1. 加载所有景点
candidates = payload_rows("attractions", 100)
# 2. 过滤开放 + 时长够
selected = [item for item in candidates
            if item.get("status") == "open"
            and item.get("visit_duration_minutes", 0) <= request.duration_minutes]
# 3. 按人群过滤（老年/亲子...），失败则保留全部
if request.groups:
    selected = [item for item in selected
                if any(g in item.get("suitable_for", []) for g in request.groups)
               ] or selected
# 4. 按偏好类别过滤
if request.preferences:
    preferred = [i for i in selected if i.get("category") in request.preferences]
    selected = preferred or selected
# 5. 贪心：按时间预算往路线里塞景点，最多5个
total = 0; result = []
for item in selected:
    duration = int(item.get("visit_duration_minutes", 60))
    if total + duration > request.duration_minutes: continue
    result.append(item); total += duration
    if len(result) >= 5: break
```

这是一个很典型的**贪心算法**：在"游玩时长预算"内尽量多地塞入合适的景点，类似课程里的"背包问题"简化版。

### 流程 4：游客反馈 → 知识沉淀（数据闭环，亮点！）

这是整个系统最巧妙的设计——**把游客反馈变成景区知识，形成数据飞轮**。

**第一步：游客提交反馈** `/api/v1/feedbacks`
```python
feedback_id = f"feedback_runtime_{uuid.uuid4().hex[:12]}"
# 生成两条记录：
#  1. feedbacks 表：原始反馈
#  2. feedback_candidates 表：可入库的"知识候选"
candidate = {
    "candidate_id": candidate_id,
    "candidate_fact": request.content,   # 把反馈内容当作"事实"
    "status": "pending_review",          # 先处于"待审核"
    "source_feedback_count": 1,
    ...
}
```

**第二步：管理员审核** `/api/v1/admin/feedback-candidates/{id}/approve`（或 `/reject`）

只有 `approve` 时才触发知识发布：
```python
if action == "approve":
    # 生成正式文档
    document_id = f"feedback_review_{candidate_id}"
    content = f"Approved visitor feedback: {candidate_fact}"
    # 写入 documents + document_chunks
    ...
    # 创建 embedding 后台任务
    task_id = f"task_embed_{...}"
    conn.execute("INSERT INTO async_tasks(...) ...")
    loop.create_task(enqueue_embedding_task(task_id, document_id))  # 异步排队
```

**等等，这里有个关键点**：`embedding` 是异步的，但**文档/分块是立即写入数据库的**。也就是说：管理员点"采纳"那一刻，这条知识就已经能通过 FTS / ILIKE 检索到并被 AI 使用了；只有"语义检索（pgvector）"要等 worker 生成好向量后才能命中。

> ⚠️ **幂等保护**：重复对同一个 candidate approve，会检测已有 task，直接返回同一个 `task_id`，不会重复建文档。

**第三步：worker 后台计算向量** `backend/app/worker.py`

```python
def process_embedding_task(task_id):
    ...
    # 安全契约：没有 embedding Key 时绝不伪造向量
    if not (EMBEDDING_API_KEY and EMBEDDING_BASE_URL):
        _set_status(task_id, "waiting_for_configuration")
        return "waiting_for_configuration"
    ...
    vector = response.json()["data"][0]["embedding"]
    if not isinstance(vector, list) or len(vector) != 1536:
        raise ValueError("embedding dimension must be 1536")  # 维度校验
    conn.execute("UPDATE document_chunks SET embedding=CAST(:vector AS vector) ...")
    _set_status(task_id, "completed")
```

这是一个典型的生产级后台任务：**状态机**（running → completed/retry/waiting_for_configuration）+ **维度校验** + **失败重试**（异常置为 `retry`）。

> 💡 这就是完整的"知识闭环"：游客反馈 → 候选 → 管理员审核 → 正式知识 → embedding → 之后能被 AI 检索引用。

## 四、公共基础设施

### 4.1 缓存层（Redis + 内存双写）
`cache_get` / `cache_set` 做了**优雅降级**：
- 优先用 Redis（生产环境分布式共享）
- Redis 不可用 → 自动退到进程内存字典 `_memory_cache`
- Redis 恢复 → 自动切回

实时数据存数据库，缓存只加速"检索"，Up to date 由文档 `updated_at` 兜底。这正是 README 说的"Redis 不可用时自动降级"。

### 4.2 限流 `enforce_public_rate_limit()`
- 生产：用 Redis 的 `INCR` + `EXPIRE` 原子计数（按 IP + 每分钟桶）
- 兜底：进程内 `_memory_rate_limits` 列表

超过 `RATE_LIMIT_PER_MINUTE`（默认60）就抛 `429`。

### 4.3 管理员认证 `admin_from_token` + 登录
- 登录：`bcrypt.checkpw` 验证密码 → 签发 JWT（HS256，8小时过期）
- 鉴权：FastAPI 的 `Depends(admin_from_token)` 从 `Authorization: Bearer xxx` 解析 JWT，非法就抛 401

### 4.4 `payload_rows()` —— 特殊的数据访问
你项目几乎所有表都长这样：`payload jsonb NOT NULL` —— **整个实体塞进一个 JSON 字段**。这是"文档型 + 关系型"的混合模式：
```python
def payload_rows(table, limit=100, offset=0):
    return [dict(row[0]) for row in conn.execute(
        text(f"SELECT payload FROM {table} WHERE park_id=:park_id ...")
    )]
```
好处是**表结构变化时无需改 SQL**，数据很灵活；坏处是不好做列级索引和强约束。这个设计值得你体会一下。

## 六、三个最重要的设计思想（复盘）

1. **降级优先（Graceful Degradation）**：整个系统处处是"主方案失败 → 备用方案"。
   - LLM 挂了 → 规则回答；embedding 没 Key → 走 FTS/ILIKE；Redis 挂了 → 内存缓存；这些设计保证了**系统永远能响应**。

2. **数据闭环 / 知识飞轮**：不是让知识"一次性写死"，而是让**游客反馈 → 管理员审核 → 自动入库 → 可被检索**，让系统越用越聪明。

3. **数据库即任务队列的"源真相"**：embedding 任务先写进 `async_tasks`，再异步 push 到 Redis 队列。即使 Redis 全挂，任务仍在库里，worker 可重试，**不丢数据**。
