## 一、现状评审

### 1.0 结论速览

原始方案的五项主张，对照当前代码的真实状态：

| 原始方案主张 | 当前现状 | 判断 |
|---|---|---|
| 使用 ReAct 模式作为主链路 | `backend/app/agents/runtime.py` 已有完整 ReAct 循环：`decide → tool_calls → execute → observe`，含步数 / 工具数 / 墙钟 / 重复调用四道护栏 | ✅ 已实现，但**控制权需要收敛** |
| 把 RAG 封装成工具，由模型决定何时调用 | `backend/app/tools/knowledge.py::search_knowledge` 已注册，带白名单授权、Pydantic 参数校验、输出不可信围栏 | ✅ 已实现，但**返回协议太薄** |
| Supervisor 多 Agent 架构 | `backend/app/agents/supervisor.py` 已有 plan → 拓扑批次并行派发 → review 收敛，含并发上限与预算 | ✅ 已实现，但**与 ReAct 形成双层控制面** |
| 多路召回 | `backend/app/services/retrieval.py` 已有实体 / pgvector / FTS / ILIKE 四路 | ⚠️ 有召回**无融合**，实际退化为单路主导 |
| 数据存 Milvus | 当前为 pgvector，无 `pymilvus` 依赖 | ⚠️ 当前规模**不必要**，但应保留可插拔接口 |

**核心判断：这个项目不需要"再实现一遍方案"，需要的是修复方案落地过程中产生的结构性缺陷。**

### 1.1 已具备的能力

必须承认，现有实现的质量高于大多数同规模项目，以下几点是有意设计而非偶然：

| 能力 | 位置 | 说明 |
|---|---|---|
| ReAct 循环 + 四道护栏 | `agents/runtime.py`、`agents/loop_guard.py` | 步数、工具调用总数、墙钟、相同调用去重，全部在信任模型之前强制 |
| 工具权限矩阵 | `tools/registry.py::ToolSpec.allowed` | 白名单是**安全边界**而非文档：未授权调用被拒，未注册工具报错 |
| 输出不可信围栏 | `tools/registry.py::sanitize_tool_output` | 工具输出注入指令会被过滤 + 截断 + 包裹为 `trusted="false"` |
| 双脑可降级 | `services/brains.py` | `LLMBrain` / `RuleBrain` 同协议，无模型时同一套骨架跑规则，并如实记录 `mode=fallback` |
| 单专员结果直通 | `agents/response_agent.py::needs_synthesis` | 只有一个专员成功时**不付第二次模型调用** |
| 依赖拓扑并行 | `agents/supervisor.py::topo_batches` | 同一批次内无依赖的任务真并发，不是假的多 Agent |
| 引用权威分级 | `services/retrieval.py::SOURCE_AUTHORITY` | `official` / `community` / `reference` 区分，答案里标注来源类型 |
| 审计与回放 | `services/audit.py`、`agent_runs` / `agent_run_steps` 表 | 每个 agent 执行、每次工具调用、每个 guard 触发都落库 |
| 反馈知识闭环 | `tools/feedback.py`、`api/admin.py` | 游客反馈 → 待审核候选 → 管理员采纳 → 创建文档 → 异步 embedding |
| 写工具幂等 | `tools/feedback.py::_idempotency_key` | 以 (conversation, content) 哈希去重，重复确认不会写两行 |

**因此本文档的立场是：在现有骨架上做外科手术，不做推倒重来。**

### 1.2 五个关键问题

#### 🔴 问题 0：把"多路召回"当成了 RAG 的全貌

原始方案对 RAG 的描述是「多路召回 + 存 Milvus」，这实际上只覆盖了 RAG 链路的**第 3 段**。
完整的 RAG 是六段：

```
[1] Query 理解 → [2] 多路召回 → [3] 融合重排 → [4] 上下文打包 → [5] 生成 → [6] 引用与评估
        ↑ 缺失          ↑ 有           ↑ 缺失          ↑ 弱           ↑ 有      ↑ 完全没有
```

每一段缺失都对应一类线上故障：

| 缺失段 | 对应故障 |
|---|---|
| Query 理解 | 多轮对话中「那它几点关门」这类指代问题检索不到任何东西 |
| 融合重排 | 多路召回的结果被固定顺序截断，实际只有一路生效（见问题 3） |
| 上下文打包 | 工具输出 600 字符截断与 2000 字符提示上限不一致，长证据被腰斩 |
| 引用与评估 | 优化完了但**无法判断是变好还是变坏** |

#### 🔴 问题 1：两套控制面在打架

- ReAct 循环在 `agents/runtime.py:245`，迭代上限 `card.max_steps`
- Supervisor 自身也是一套 plan → observe → review 循环，在 `agents/supervisor.py:107`，
  上限 `AGENT_MAX_DELEGATION_ROUNDS`
- `AGENT_MAX_STEPS = 6`（`core/config.py:72`）同时被两边读取

后果：**一个请求内存在双层规划、双层循环**，两者都在回答"下一步做什么"，但互不感知：
Supervisor 已经通过 `instruction` 限定了专员的意图和动作范围，专员的 ReAct 循环实际只剩
"按指定工具跑一遍"的自由度。原始方案想表达的"模型自主决定何时调用 RAG"，在
Supervisor 先行规划的前提下，自主性已经被预先收窄。

这不是实现 bug，而是**架构层面的职责重叠**，必须明确谁是唯一控制面。

#### 🔴 问题 2：每轮请求跑两次决策，且可能互相矛盾

`services/orchestrator.py:113` 在 `LLM_MODE=agent` 时先执行 `classify_with_cache`（一次 LLM 调用），
随后 `run_supervisor` 内部再执行 `brain.plan`（第二次 LLM 调用）。

后果：

1. **两倍 token 与两段串行延迟**，且都在用户可见响应之前
2. 两个决策点可能给出不一致的判断（分类器说 qa，Planner 派 route_agent）
3. 与 ReAct 的设计哲学冲突：模型还没进入思考，意图已被外部锁死

#### 🟠 问题 3：多路召回没有融合，四路退化成一路

这是最隐蔽也最影响效果的问题。`services/retrieval.py::retrieve` 的候选收集方式：

```python
candidates.extend(...)   # 第 1 层：实体命中
candidates.extend(...)   # 第 2 层：pgvector
candidates.extend(...)   # 第 3 层：FTS
candidates.extend(...)   # 第 4 层：ILIKE
```

随后 `select_diverse` **按 candidates 的原始顺序**遍历并截断到 `top_k`：

```python
for item in items:                 # items 就是 candidates，顺序 = 层顺序
    ...
    selected.append(item)
    if len(selected) >= top_k:     # top_k 默认 5
        return selected
```

后果非常确定：

- 实体层命中多少，就占掉前几个名额
- 剩下的名额被向量层按 distance 顺序吃掉
- **FTS（第 3 层）和 ILIKE（第 4 层）几乎永远进不了 `top_k`**

同时缺少融合所需的要素：没有每路配额（`RETRIEVAL_TOP_K` 是全局的）、没有跨路打分
（各路 score 量纲不同：entity 无分数、vector 是 cosine distance、FTS 无分数）、
没有 RRF 或加权融合。

**"多路召回"目前只是"四路各查一遍然后丢掉后面的"。**

#### 🟠 问题 4：`search_knowledge` 返回协议太薄，模型无法区分「库里没有」和「库里有但不相关」

当前返回：

```python
{"query": ..., "total": n, "items": [...], "citations": [...]}
```

缺失的关键信号：

| 缺失信号 | 造成的后果 |
|---|---|
| 每条的检索路径与得分 | 模型无法判断证据强弱，只能一视同仁地引用 |
| 整体置信度 / 空结果语义 | `total=0` 与 `total=3`（全不相关）在模型看来差别只在于长度 |
| 走过的召回路径 | 排查"为什么没检索到"时只能猜 |
| `insufficient_evidence` 标志 | 抑制幻觉**完全依赖 system prompt 喊话**，无结构化约束 |

#### 🔴 问题 5（P0 越权）：写工具的确认门由模型参数决定

`tools/feedback.py::create_feedback_candidate` 的写入与否，取决于模型生成的 `confirmed` 参数：

```python
if not args.confirmed:
    return {"written": False, ...}     # 只存草稿
# confirmed=True → 直接 INSERT feedbacks + feedback_candidates
```

对比两条路径：

| 路径 | 是否有额外保护 |
|---|---|
| `RuleBrain` | 有。`brains.py::_explicit_submission` 用关键词判断访客是否明确要求提交，未明确则根本不规划该工具 |
| `LLMBrain` | **无。** 模型直接输出 `confirmed=true` 即可写库 |

`tests/test_multi_agent.py:419` 的 `test_feedback_write_requires_an_explicit_visitor_confirmation`
只覆盖了 `RuleBrain` 路径，**所以这个洞在测试里是绿的**。

正确设计：写入许可必须由**工具层校验访客的真实轮次消息 + 是否存在待确认草稿**，
而不是信任模型传入的布尔值。模型可以出错，也可以被 prompt 注入诱导。

#### 附带发现（非本次核心，但要记录）

| 发现 | 位置 | 影响 |
|---|---|---|
| `embedding vector(1536)` 维度写死 | `sql/init.sql:11` | 换 embedding 模型需改表 + 重建索引 |
| 工具为同步函数，走 `asyncio.to_thread` | `tools/registry.py:230` | 同步 SQLAlchemy 引擎在并发下打满线程池 |
| 工具输出压缩 600 字符 vs 提示上限 2000 | `registry.py:141` vs `config.py:80` | 长证据被静默腰斩 |
| `select_diverse` 用内容 SHA1 去重 | `retrieval.py:138` | RRF 融合后同一内容会从多路出现，**必须保证融合幂等** |
| `evaluation_questions` 表存在但未使用 | `sql/init.sql:12` | 无评测基线 |
| 专员拿不到其他专员的 observations | `runtime.py:226` `local_observations` | 并行专员重复检索；第二次相同调用被 `LoopGuard` 误判为 `RepeatedToolCall` |

## 二、Milvus 取舍判断

**结论：当前阶段不引入 Milvus 作为主路径，但先抽象存储接口，使其成为可插拔实现。**

### 2.1 为什么现在不必要

| 维度 | pgvector（现状） | Milvus |
|---|---|---|
| 适配数据规模 | 万级 chunks 足够 | 十万至亿级才有明显收益 |
| 运维成本 | 已在运行，零新增组件 | 新增一套有状态集群 |
| 一致性 | 同库事务，写完立即可见 | 索引异步构建，刚写入的数据可能检索不到 |
| 正文存储 | 同表返回，一次查询搞定 | 需 scalar field 或回表 PostgreSQL |
| 额外复杂度 | HNSW 索引已建（`sql/init.sql:14`） | +pymilvus 依赖 +collection +partition +一致性级别调优 |

本项目的知识库是「40 个景点 + 37 项设施 + 24 条官方问答 + 20 篇知识」量级，
对应 chunk 数量在数百到数千。在这个规模上，**pgvector 的 HNSW 检索延迟与 Milvus 无实质差异，
而召回质量的瓶颈在融合与重排，不在 ANN 引擎**。换存储不会让答案变好。

### 2.2 Milvus 在这里唯一不可替代的价值

`sql/init.sql:11` 的 `embedding vector(1536)` 把维度固化在表结构里。
Milvus collection 的 `dim` 是建集合时的参数，换 embedding 模型只需重建 collection，
不需要修改表结构。这是 Milvus 在本项目中**真正能解决的问题**。

### 2.3 因此的策略

```
Phase A：抽象 VectorStore 接口 → pgvector 保持唯一后端（零行为变化）
Phase B：双写影子索引 → 评测集对比 → 精度不退才切读路径
```

详见 [3.4 Milvus 落地路径](#34-milvus-落地路径)。

## 三、目标架构

### 3.0 分层总览

```
┌─ L4 接入层 ──────────────────────────────────────────────────────┐
│ FastAPI /api/v1/chat (SSE) · 幂等键 · 限流 · 请求级预算           │
├─ L3 Agent 控制面（唯一控制面）───────────────────────────────────┤
│ Entry Router → Planner(≤1 次) → Specialists(ReAct 自主迭代)      │
│              → Critic → 答案                                     │
│ 约束：不再有第二次 review 循环；ReAct 迭代权只属于专员            │
├─ L2 能力层（全部工具化，白名单 + 强制校验）───────────────────────┤
│ rag_search · catalog_query · route_plan · realtime · feedback(写) │
├─ L1 检索层（RAG 六段完整链路）───────────────────────────────────┤
│ 理解 → 5 路召回 → RRF 融合 → 精排 → 证据打包 → 评估/追踪          │
├─ L0 存储层（源真相 + 可换索引）───────────────────────────────────┤
│ PostgreSQL(源真相) · pgvector|Milvus(索引) · Redis(缓存/队列)     │
└──────────────────────────────────────────────────────────────────┘
```

**单向依赖**：L3 只能通过 L2 的工具触达数据；L2 只能通过 L1 检索层触达索引；
L1 只能通过 L0 的 `VectorStore` 接口触达向量库。任何越层调用都是缺陷。

### 3.1 控制面重构

#### 3.1.1 Supervisor 降级为单次 Planner

```python
# 现状：supervisor.py:107 —— 外层 for 循环，与专员内部 ReAct 形成双层循环
for round_index in range(max_steps):
    current_plan = await brain.plan(...)
    ...
    current_plan = await _follow_up(brain, context)   # 第二次决策

# 目标：Planner 只做一次规划，收敛判断交给专员与预算
async def run_planner(context: RunContext, brain: Brain) -> Plan:
    """输出 goal + tasks，不做 iterate。"""
    ...

async def run_specialist(agent, instruction, context, brain) -> AgentResult:
    """内部 ReAct 自由迭代，工具选择由模型自主决定。"""
    ...

# 专员失败 / 证据不足 → 有上限的 replan（而非重跑 plan→delegate→review）
```

**改变语义**：

| 环节 | 现状 | 目标 |
|---|---|---|
| 规划次数 | 最多 `AGENT_MAX_DELEGATION_ROUNDS`(3) 次 | 1 次，失败时最多 +1 次 replan |
| 迭代归属 | 双层（supervisor + specialist） | 单层（specialist ReAct） |
| 收敛判断 | supervisor 的 `review` LLM 调用 | 预算 + 专员的 `insufficient_evidence` 信号 |
| 最坏模型调用数 | peak 5-6 次 | peak 3-4 次 |

**收益**：墙钟从 45s 上限（`AGENT_REQUEST_TIMEOUT_SECONDS`）收敛到典型 12-20s；
消除"supervisor 已决定作答、专员还在检索"的空转。

#### 3.1.2 砍掉必经的 LLM 分类器，改为三条入口

`services/intent.py::classify_with_cache` 不再作为所有请求的必经节点，改为**分级入口**：

| 入口 | 触发条件 | 路径 | 预估占比 |
|---|---|---|---|
| A. 规则快路径 | `keyword_route` 高置信命中 | 直达专员，**0 次规划 LLM 调用** | ~35% |
| B. 轻量路径 | 单意图且消息短 | 1 次模型调用直出「专员 + instruction」 | ~45% |
| C. 完整规划 | 多意图 / 跨域 / 约束冲突 | Planner + 多专员并行 | ~20% |

注意 `response_agent.needs_synthesis()`（`response_agent.py:41`）已经实现了
"单专员成功则直通、不付第二次模型调用"的思路。这一优化思路是正确的，
现在把它扩展一层到**入口**即可，属于同一设计语言的延续。

**延迟与成本估算**（假设单次模型调用 1.2s）：

| 场景 | 现状调用数 | 目标调用数 | 延迟改善 |
|---|---|---|---|
| 简单问答「五花海海拔多少」 | 分类 1 + 规划 1 + ReAct 2 = 4 | 规则直达 0 + ReAct 2 = 2 | ~-40% |
| 单意图票务问题 | 4 | 轻量 1 + ReAct 2 = 3 | ~-25% |
| 复杂路线规划（雨天+老人+设施） | 5-6 | Planner 1 + 2 专员 ReAct 4 + 汇总 1 = 6 | 持平但并行度更高 |

#### 3.1.3 分层模型 + 四级预算

**分层模型**（同一端点下按任务选模型，不引入新供应商）：

| 层级 | 用途 | 要求 |
|---|---|---|
| Tier-A（强模型） | 最终答案生成、复杂约束规划 | 质量优先 |
| Tier-C（廉价快速） | 意图判定、Planner、Critic、rerank 打分、实体抽取 | 延迟与成本优先 |

**四级预算**（在现有 `agents/loop_guard.py::Budget` 上扩展）：

| 预算 | 现状 | 目标 |
|---|---|---|
| 墙钟 | ✅ `AGENT_REQUEST_TIMEOUT_SECONDS` | 保留 |
| 工具调用数 | ✅ `AGENT_MAX_TOTAL_TOOL_CALLS` | 保留 |
| 步骤数 | ✅ `AGENT_MAX_STEPS * 4` | 保留，但语义改为"仅计专员 ReAct 步" |
| **token 数** | ❌ 无 | **新增**，按 Tier 分别计量 |
| **模型调用数** | ❌ 无 | **新增**，硬上限，超限走降级 |

任一超限时**降级而非报错**——沿用现有 `orchestrator._salvage` 的策略：
用已有 observations 走 `render_rule_answer`，返回带来源兜底话术的答案。

### 3.2 RAG 六段完整链路

```
Query
  │
  ├─[1] Query 理解
  │     指代消解（多轮时：「那它几点关门」→「五花海几点关门」）
  │     约束抽取（预算分钟 / 人群 / 天气 / 无障碍）
  │     查询规范化（去口语、补全省略）
  │     可选 HyDE：生成假设答案再取向量
  │     ⚙️ Tier-C 模型，仅多轮或短查询触发；单轮长查询跳过，避免无谓延迟
  │
  ├─[2] 多路召回（asyncio.gather 并行，每路独立超时，单路失败不影响整体）
  │     R1 实体路   已知 POI 名精确命中        ← 保留现有 known_entity_ids
  │     R2 稠密路   VectorStore.search        ← pgvector 或 Milvus
  │     R3 稀疏路   BM25 / 中文分词 FTS        ← 替换现有 'simple' FTS
  │     R4 结构路   票价/时间/规则按字段命中    ← 新增：payload 字段精确匹配
  │     R5 图谱路   景点—设施—观光车邻接扩展    ← 可选，route.py 已有邻接数据
  │
  ├─[3] 融合（核心修复）
  │     RRF: score(d) = Σ_r w_r · 1 / (k + rank_r(d))，k=60
  │     每路配额：防止单路独占 top_k
  │     内容指纹去重：保证融合幂等
  │     输出 fusion_trace：每路命中数、贡献占比、被丢弃原因
  │
  ├─[4] 精排（可选）
  │     cross-encoder / bge-reranker → top_k
  │     ⚠️ 阈值只在精排后设置：现有 RETRIEVAL_MAX_DISTANCE=0.72 作用在
  │        混合量纲候选上（entity 无分数、vector 是 cosine distance），本身不成立
  │
  └─[5] 证据打包（带置信度）
        {items, routes_used, empty_routes, top_score, margin, hit_entities,
         confidence, insufficient_evidence}
```

#### 3.2.1 RRF 融合算法

```python
# backend/app/services/fusion.py
def reciprocal_rank_fusion(
    route_results: dict[str, list[dict]],   # route_name -> 已按该路得分排序的候选
    *,
    weights: dict[str, float] | None = None,
    k: int = 60,
    quota: dict[str, int] | None = None,    # 每路进入融合的最大条数
    top_k: int = RETRIEVAL_TOP_K,
) -> tuple[list[dict], dict]:
    """把多路召回融合成一份排序结果。

    返回 (items, fusion_trace)。fusion_trace 记录每路贡献，用于评测哪一路真正有用。
    """
    scores: dict[str, float] = {}
    payload: dict[str, dict] = {}
    paths: dict[str, set[str]] = {}
    weights = weights or {}
    quota = quota or {}

    for route, hits in route_results.items():
        w = weights.get(route, 1.0)
        limit = quota.get(route, len(hits))
        for rank, hit in enumerate(hits[:limit], start=1):
            key = _content_fingerprint(hit)       # 按内容指纹聚合，保证跨路幂等
            scores[key] = scores.get(key, 0.0) + w / (k + rank)
            payload.setdefault(key, hit)
            paths.setdefault(key, set()).add(route)

    ordered = sorted(scores.items(), key=lambda kv: (-kv[1], kv[0]))
    items = []
    for key, score in ordered[:top_k]:
        item = dict(payload[key])
        item["rrf_score"] = round(score, 6)
        item["retrieval_paths"] = sorted(paths[key])
        item["retrieval"] = "+".join(sorted(paths[key]))   # 兼容现有 citations 字段
        items.append(item)

    trace = {
        "routes": {r: len(h) for r, h in route_results.items()},
        "contribution": _contribution(route_results, items),
        "fused": len(items),
    }
    return items, trace
```

**权重初值建议**（后续由评测集调优，不靠直觉）：

| 路 | 初始权重 | 依据 |
|---|---|---|
| `entity` | 1.5 | 精确名称命中，中文无分词场景下最可靠 |
| `dense` | 1.0 | 语义召回主力 |
| `sparse` | 1.0 | 关键词精确性 |
| `structured` | 1.2 | 票务/时间类字段匹配准确率高 |
| `graph` | 0.7 | 扩展召回，噪声较高 |

**每路配额初值**：`top_k * 2`，保证每路都有机会进入融合。

#### 3.2.2 无融合 vs 有融合的行为对比

以 `top_k=5`、问题「五花海怎么去，附近有卫生间吗」为例：

| 阶段 | 现状（固定顺序拼接） | 目标（RRF 融合） |
|---|---|---|
| 实体层命中 | 五花海 3 条 → **占满前 3 位** | 3 条参与打分 |
| 向量层 | 剩 2 位按 distance 取 | 5 条参与打分 |
| FTS | **永远进不了 top_k** | 3 条参与打分 |
| ILIKE | **永远进不了 top_k** | 2 条参与打分 |
| 最终 top_k | 3 实体 + 2 向量，**无设施信息** | 五花海 2 + 设施 2 + 路线 1，**跨路证据都在** |

这正是"多路召回"应该带来的效果：**让不同检索维度各自的最优结果都有机会进入最终上下文**。

**`confidence` 判定规则**（写进工具层，不交给模型）：

| 条件 | `confidence` | 工具描述中的强制指令 |
|---|---|---|
| `top_score` 高 且 `margin` 大 且 ≥1 条 official | `high` | 可正常作答并引用 |
| 有结果但 `top_score` 低 或 `margin` 小 | `medium` | 作答时须声明"资料未明确" |

无 `official` 来源。这是结构化约束，比在 system prompt 里写十遍"不要编造"更可靠。

### 3.3 Agent 工具化

#### 3.3.1 请求级检索缓存（解决问题 3.3 中的重复检索）

**现状缺陷**：`agents/runtime.py:226` 的 `local_observations` 是专员私有的；
`build_messages` 调 `handoff_packet` 时只传了 `context.summary()`（专员的答案摘要），
**没有传 `context.observations`**（工具级观察）。因此两个并行专员检索同一 query 时：

1. 各自跑一遍完整检索 → token 与延迟翻倍
2. 第二个相同参数的调用被 `LoopGuard`（`max_repeats=1`）拦下，返回
   `RepeatedToolCall`——专员拿到的是**错误语义**（"你别重复调用"），而非"这是已有结果"

**目标设计**：

```python
# backend/app/services/retrieval_cache.py
class RetrievalCache:
    """请求级检索缓存：同一次请求内，相同 (query, top_k, filters) 只检索一次。"""

    def __init__(self) -> None:
        self._hits: dict[str, dict] = {}
        self._stats = {"hits": 0, "misses": 0}

    @staticmethod
    def key(query: str, top_k: int, filters: dict | None = None) -> str:
        raw = f"{query.strip().lower()}|{top_k}|{json.dumps(filters or {}, sort_keys=True)}"
        return hashlib.sha256(raw.encode("utf-8")).hexdigest()[:24]

    def get(self, key: str) -> dict | None: ...
    def put(self, key: str, value: dict) -> None: ...
```

**挂载点**：`RunContext.artifacts["retrieval_cache"]`，随请求生命周期创建与销毁。

> ⚠️ **不能**把缓存挂到 `RunContext.absorb` 走的 `context.observations` 上——
> 那是审计口径，语义不同。缓存是执行优化，observations 是审计记录，混用会让审计失真。

**同时修正传递语义**：`handoff_packet` 增加 `context.observations` 的工具级摘要，
让后续专员知道"哪些检索已经做过了"，而不是收到一个重复调用错误。

#### 3.3.2 写工具强制校验（P0）

**修复原则：写入许可由工具层根据访客真实轮次消息判定，不信任模型传入的布尔值。**

**架构约束**：`ToolSpec.func` 的签名需要能拿到访客消息。当前是 `spec.func(parsed)`，

这是**工具层的一次签名升级**，会影响全部工具，但收益明确：任何需要"真实会话上下文"
才能安全执行的工具（现在的写工具，将来的确认类、支付类、预约类）都有了统一入口。

#### 3.3.3 工具 async 化

现状 `tools/registry.py:230`：同步函数走 `asyncio.to_thread`。理由是"阻塞的数据库和 HTTP 调用
不能占住事件循环"，但 `asyncio.to_thread` 用的是**默认线程池**，在并发请求下会成为瓶颈，
且与 `AGENT_MAX_CONCURRENCY` 的语义不匹配。

目标：

1. 数据库访问层提供 `AsyncEngine`（`sqlalchemy.ext.asyncio`），工具改 `async def`
2. `ToolRegistry.execute` 的 `iscoroutinefunction` 分支保留（兼容第三方同步工具），
   但自有工具全部 async
3. 工具超时（`AGENT_TOOL_TIMEOUT_SECONDS=8`）与请求超时（45s）保持 1:5 以上比例，
   保证单工具超时不会直接耗尽请求预算

#### 四条硬规则

| # | 规则 | 原因 |
|---|---|---|
| 1 | **PostgreSQL 永远是源真相，Milvus 是可重建索引。** 写入顺序：PG 先提交，再写 Milvus | Milvus 数据丢失可从 PG 全量重建；读路径不依赖 Milvus 的持久化保证 |
| 2 | 一致性默认 `Bounded`；`reindex` 与知识审核通过后强制 `flush()` | 否则"管理员刚发布的知识搜不到"，这是最容易被投诉的体验缺陷 |
| 3 | **多路召回在应用层融合**，不用 Milvus 的 `hybrid_search` ranker | 权重与 RRF 只有一个真相源（L1 融合层），可评测、可回放 |
| 4 | **降级可用**：Milvus 不可用时标记 `empty_routes=["dense"]`，其余四路照常出结果 | 向量库故障不能让整个问答失败 |

#### 监控

每路的 `hit_contribution`（该路对最终 top_k 的贡献占比）写入 trace 与评测报告。
**某一路长期贡献为 0，就把它砍掉**——这是判断"多路召回到底有没有用"的唯一客观证据，
也是防止为了架构好看而保留无效路径的机制。

| **P1-1** | 评测集 120 条 + `scripts/rag_eval.py` 出基线 | 低 | **后续所有改动的依据** | — |
| **P1-2** | RRF 融合 + 每路配额 + 内容指纹幂等 | 中 | **多路召回真正生效** | P1-1 |
| **P1-3** | `search_knowledge` 返回协议加置信度 | 低 | 抑制幻觉 | P1-2 |
| **P2-1** | Supervisor 降级单次 Planner；三条入口分级 | 中高 | 延迟 -40%、成本 -50% | P1-1 |
| **P2-2** | 工具 async 化 + `AsyncEngine` | 中 | 并发能力 | P0-2 |
| **P2-3** | 分层模型 + token/调用数预算 | 低 | 成本可控 | P2-1 |
| **P3-1** | `VectorStore` 抽象 + `PgVectorStore` | 中 | 为 Milvus 铺路 | P1-2 |
| **P3-2** | Milvus 影子索引 + 评测对比 + 切换 | 中 | 维度参数化 / 可扩展 | P3-1 |

### 关键顺序原则

> **P1 的融合与评测必须早于 P2 的控制面重构。**

理由：P2 会改变请求路径与模型调用次数，延迟一定下降。但如果没有 P1 的评测基线，
**召回质量是升是降将无法判断**——延迟变好会掩盖召回变差。
这正是当前项目最大的隐患：所有改动都无法证伪。

### 每阶段的完成定义

| 阶段 | 完成定义 |
|---|---|
| P0 | 新增测试覆盖 LLMBrain 路径的未确认写入，测试通过；现有 536 行测试全绿 |
| P1-1 | `reports/eval_baseline.json` 产出，含 recall@5 / MRR / 每路贡献 |
| P1-2 | 同一评测集 recall@5 **不低于**基线（目标 +15%）；`test_rrf_lets_low_priority_route_into_top_k` 通过 |
| P1-3 | 空结果场景下模型输出兜底话术，不再出现推断性内容 |
| P2 | 简单问答模型调用数 ≤2；P95 延迟较基线下降 ≥30%；测试全绿 |
| P3 | `VECTOR_BACKEND` 双后端评测报告产出；Milvus 不可用时请求成功率不下降 |
